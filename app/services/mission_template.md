연습문제 1: 패치 릴리즈(Hotfix) – 토큰 갱신 오류 수정 v1.1.1
1) 시나리오 요약
- 현재 v1.1에서 일부 사용자의 토큰 갱신 API가 간헐적으로 500 오류를 반환합니다.
- 원인: 동시 갱신 요청 시 토큰 저장소 충돌. 해결: 낙관적 잠금 도입, 재시도 지수 백오프.
- 신규 에러 코드 409_REFRESH_CONFLICT 추가. API 스펙은 동일(하위 호환).
- 유지보수성 향상을 위한 로그 필드 request_id 추가.

2) 제공 정보
- 이전 버전: v1.1
- 대상 API: POST /api/v1/auth/token/refresh
- 변경점:
  - 500_INTERNAL_ERROR 일부 케이스가 409_REFRESH_CONFLICT로 대체
  - 응답 헤더 X-Request-Id 추가
- 배포 대상: Backend API 서버
- 릴리즈 타입: Patch

3) 필수 작성 항목(템플릿에 채우기)
- 문서 기본 정보: 제목, 작성일, 작성자, 버전 v1.1.1
- 개요: 50자 이내(핵심: 갱신 충돌 핫픽스, 에러 코드 보정)
- 버전 정보 표: 이전 v1.1 → 현재 v1.1.1, Patch, 배포 대상, 버전 규칙
- 주요 변경 사항 표: 수정(토큰 갱신 충돌 처리), 기타(에러 코드 추가, 헤더 추가)
- Breaking Changes: 없음(명시)
- 마이그레이션 가이드: 클라이언트는 409 시 재시도 백오프 적용 안내(예상 소요 0.5~1일)
- Known Issues: 토큰 저장소 지연 시 간헐 409 지속 가능, 우회 방안(최대 3회 재시도)
- 향후 계획: v1.2에서 소셜 로그인 예정 등
- 참고 정보: 관련 장애 리포트, 로그 포맷 문서 링크

4) 간단 체크리스트
- Patch 릴리즈로 분류했는가
- 개요 50자 준수
- Breaking Changes에 “없음” 명시
- 변경사항 표에 영향도 기입

연습문제 2: 마이너 릴리즈 – OAuth 소셜 로그인 추가 v1.2.0
1) 시나리오 요약
- Google/Apple OAuth 로그인 추가, 기존 기본 로그인 유지(하위 호환).
- 신규 엔드포인트:
  - POST /api/v1/auth/oauth/start
  - POST /api/v1/auth/oauth/callback
- 신규 에러 코드: 401_OAUTH_INVALID_STATE, 401_OAUTH_EXPIRED_CODE
- Rate Limit: OAuth 관련 엔드포인트 분당 15회
- 향후 /auth/login/basic는 v2.0에서 제거 예정(이번 버전엔 Deprecation Notice만 노출).

2) 제공 정보
- 이전 버전: v1.1.1
- 배포 대상: Backend API 서버, 프론트 연동 모듈
- 릴리즈 타입: Minor
- 응답 예시(신규):
  {
    "token": "eyJ...",
    "provider": "google",
    "profile": {"email": "user@example.com"}
  }

3) 필수 작성 항목
- 문서 기본 정보: 제목, 작성일, 작성자, 버전 v1.2.0
- 개요: 50자 이내(소셜 로그인 추가, 레이트 제한)
- 버전 정보 표: 이전 v1.1.1 → v1.2.0, Minor, 배포 대상, 버전 규칙
- 주요 변경 사항 표: 신규 기능(OAuth), 보안(콜백 검증 강화), 기타(Rate Limit 15회)
- Breaking Changes: 없음. 단, “/auth/login/basic” 폐기 예정 고지 포함
- 마이그레이션 가이드: 프론트에 OAuth 플로우 추가, 상태값(state) 검증, 예상 2~3일
- Known Issues: 일부 기업망에서 Google OAuth 차단 가능, 우회 방안(화이트리스트)
- 향후 계획: v2.0에서 basic 로그인 제거 예정 명시(일정)
- 참고 정보: OAuth 보안 가이드, 프로바이더 콘솔 설정 문서

4) 체크리스트
- Deprecation Notice 명시
- 에러 코드, Rate Limit 반영
- 하위 호환 유지로 Breaking Changes=없음 처리

연습문제 3: 메이저 릴리즈 – 토큰 포맷 변경 및 v2 엔드포인트 v2.0.0
1) 시나리오 요약
- 인증 토큰을 JWT → PASETO로 변경(서명·검증 방식 변경).
- 엔드포인트 버전 업: /api/v1 → /api/v2
- 로그인 응답 구조 변경: token_type 추가, user 필드 스키마 변경
- 구 v1 엔드포인트 6개월 유지 후 폐기 예정

2) 제공 정보
- 이전 버전: v1.2.0
- 릴리즈 타입: Major
- 새 응답 예시:
  // v1
  { "token": "eyJ...", "user": {"id": 1, "email": "a@b.com"} }
  // v2
  { "token": "v2.local....", "token_type": "PASETO", "user": {"user_id": 1, "email": "a@b.com"} }
- 요구 대응:
  - 클라이언트는 token_type 검사 및 PASETO 지원 필요
  - user.id → user.user_id로 필드명 변경
  - 베이스 URL 변경(/v2)

3) 필수 작성 항목
- 문서 기본 정보: 제목, 작성일, 작성자, 버전 v2.0.0
- 개요: 50자 이내(토큰 포맷 변경, v2 전환)
- 버전 정보 표: 이전 v1.2.0 → v2.0.0, Major, 배포 대상, 버전 규칙
- 주요 변경 사항 표: 보안(PASETO), Breaking(필드명 변경), 기타(베이스 경로 변경)
- Breaking Changes: v1 vs v2 JSON 예시(위 제공), 영향도 및 수정 필요 항목 명시
- 마이그레이션 가이드: 엔드포인트 교체, 응답 파서 수정, 토큰 검증 라이브러리 교체, 예상 3~5일
- Known Issues: 일부 라이브러리의 PASETO 호환성 이슈, 임시 우회(서버측 호환 모드)
- 향후 계획: v1 폐기 일정(6개월 뒤), SDK 업데이트 일정
- 참고 정보: PASETO 스펙, v2 API 명세 링크

4) 체크리스트
- Major 분류 사유 명확화
- JSON Before/After 포함
- 폐기 일정과 커뮤니케이션 포함

연습문제 4: 인프라/운영 변경 – 레이트 리밋 헤더 표준화 v1.1.2
1) 시나리오 요약
- 기존 비표준 헤더 X-RateLimit-Remaining 등을 RFC 표준 형태로 정리:
  - 표준화: RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset
  - 429 응답 시 Retry-After 헤더 추가
- 기능은 동일, 클라이언트 표시 로직 조정 필요(하위 호환: 기존 헤더도 1분간 동시 제공, 이후 제거 예고)

2) 제공 정보
- 이전 버전: v1.1.1
- 릴리즈 타입: Patch(기능 추가/수정 없음, 헤더 표준화)
- 영향: 헤더 파싱 로직 업데이트 권장
- Deprecation: X-RateLimit-* 30일 후 제거 예정

3) 필수 작성 항목
- 문서 기본 정보: 제목, 작성일, 작성자, 버전 v1.1.2
- 개요: 50자 이내(레이트 리밋 헤더 표준화)
- 버전 정보 표: 이전 v1.1.1 → v1.1.2, Patch, 배포 대상, 버전 규칙
- 주요 변경 사항 표: 수정(헤더 표준화), 기타(Retry-After 추가), 낮음~중간 영향
- Breaking Changes: 없음(동시 제공 기간 안내 및 제거 일정 명시)
- 마이그레이션 가이드: 헤더 파싱 이중 대응 30일, 예상 0.5~1일
- Known Issues: 일부 프록시가 Retry-After를 정수만 허용, 형식 주의
- 향후 계획: 제거 날짜 명시
- 참고 정보: IETF RateLimit 헤더 초안/문서 링크

4) 체크리스트
- Patch로 분류
- Deprecation 일정 명확
- 영향도 과대/과소평가 금지
