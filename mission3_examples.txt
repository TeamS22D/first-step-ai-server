**미션 2:**  동료의 잘못된 코드 수정 요청하기

**당신의 역할:** 입사 1년차 백엔드 개발자 '최개발'. 현재 '베타 스쿼드' 소속으로 API 개발을 담당하고 있습니다.


**주어진 상황:**
코드 리뷰 중: 2년차 선배인 '박선배'가 작성한 '사용자 인증 API' 코드를 리뷰하고 있습니다.
발견한 문제:

비밀번호 검증 로직에서 평문(plaintext)으로 비밀번호를 비교하고 있습니다. 해시 처리가 되어 있지 않아 보안에 심각한 취약점이 있습니다.
데이터베이스 쿼리가 반복문 안에서 N번 실행되어 N+1 문제가 발생하고 있습니다. 대량의 데이터 처리 시 성능 저하가 예상됩니다.


고민 포인트: 박선배는 나보다 경력이 많고, 평소 자존심이 강한 편입니다. 잘못 지적하면 관계가 불편해질 수 있습니다.

**미션 목표:**
박선배에게 코드의 문제점을 지적하고 수정을 요청하세요.

**핵심 성공 가이드:**
감정적 표현 대신 기술적 근거를 명확히 제시하세요. (예: "이 방식은 OWASP 보안 가이드에서 권장하지 않는 방식입니다")
상대방을 비난하는 표현을 피하고, 코드 자체에 집중하세요. ("선배님이 잘못했다" ❌ → "이 코드에서 개선할 부분이 있는 것 같아요" ⭕)
가능하면 구체적인 해결 방안이나 대안 코드를 함께 제시하세요.


### **미션 3: 좋은 케이스 10가지**
[Good Case 1]
User: 선배님, 코드 리뷰하다가 궁금한 점이 있어서요. 비밀번호 검증 부분에서 평문으로 비교하고 계신데, 혹시 bcrypt나 SHA-256 같은 해시 알고리즘을 사용하는 게 어떨까요? OWASP 가이드라인에서도 평문 저장은 보안 취약점으로 분류하고 있어서요. 제가 bcrypt 적용 예시 코드를 공유해드릴 수 있습니다.
AI: 아, 그 부분? 음... 확실히 해시 처리가 맞긴 하지. 좋아, bcrypt로 수정해볼게. 예시 코드 공유해줘.
[Good Case 2]
User: 선배님, 이 부분 잠깐 여쭤봐도 될까요? 반복문 안에서 DB 쿼리를 계속 호출하고 계신데, N+1 문제가 발생할 수 있을 것 같습니다. JOIN이나 서브쿼리로 한 번에 가져오면 성능이 훨씬 개선될 것 같은데, 제가 수정안을 작성해봐도 괜찮을까요?
AI: 아, N+1? 맞네. 내가 놓쳤구나. 수정안 한번 보여줘봐.
[Good Case 3]
User: 선배님, 인증 API 코드 정말 깔끔하게 작성하셨네요! 다만 한 가지 보안 관련해서 제안드리고 싶은 부분이 있는데요. 비밀번호 비교 로직에서 해시 처리를 추가하면 더 안전할 것 같습니다. 실제로 이전 프로젝트에서 비슷한 케이스 때문에 보안 감사에서 지적받은 적이 있었거든요.
AI: 오, 그런 경험이 있었구나. 좋은 지적이야. 그럼 해시 처리 추가해볼게.
[Good Case 4]
User: 선배님, 코드 전반적으로 로직이 명확해서 이해하기 좋았습니다. 한 가지 성능 부분에서 개선 여지가 있을 것 같은데, 현재 쿼리 방식이 데이터가 많아지면 병목이 생길 수 있을 것 같아요. 제가 프로파일링 결과를 공유드려도 괜찮을까요?
AI: 프로파일링까지 해봤어? 오케이, 한번 보여줘. 성능 이슈면 당연히 고쳐야지.
[Good Case 5]
User: 선배님, 리뷰하면서 궁금한 게 생겼는데요. 이 부분에서 평문 비교를 하신 특별한 이유가 있으신가요? 제가 알기로는 보통 해시 처리를 하는 게 표준인 것 같아서요. 혹시 제가 놓친 부분이 있다면 설명 부탁드립니다.
AI: 아, 특별한 이유는 없고... 그냥 빠르게 구현하느라 놓쳤네. 맞아, 해시 처리가 맞지. 지적 고마워.
[Good Case 6]
User: 선배님, 이 코드 구조는 정말 잘 짜신 것 같은데, 한 가지만 여쭤보고 싶습니다. 반복문 안의 쿼리 호출이 성능에 영향을 줄 수 있을 것 같은데, 배치 쿼리로 최적화하는 건 어떨까요? 제가 테스트해보니 응답 시간이 약 70% 개선되더라구요.
AI: 70%나? 와, 그 정도면 확실히 개선이 필요하겠네. 좋아, 배치 쿼리로 수정할게. 테스트 결과도 공유 부탁해.
[Good Case 7]
User: 선배님, 코드 리뷰 중인데 하나 확인하고 싶은 부분이 있습니다. 비밀번호 처리 부분에서 보안 강화가 필요할 것 같은데, 회사 보안 정책에 따르면 반드시 해시 알고리즘을 사용하도록 되어 있거든요. 혹시 이 부분 수정 가능하실까요?
AI: 아, 회사 보안 정책? 그럼 당연히 고쳐야지. 내가 정책을 제대로 안 봤네. 고마워, 바로 수정할게.
[Good Case 8]
User: 선배님, 전체적인 코드 플로우는 완벽한데, DB 접근 부분에서 최적화 여지가 보이네요. 현재 방식은 작은 데이터셋에서는 문제없지만, 스케일이 커지면 이슈가 될 수 있을 것 같습니다. 제가 최적화 방안을 문서로 정리해서 공유드려도 될까요?
AI: 오, 스케일을 고려해주다니 센스 있네. 좋아, 문서 보내줘. 같이 검토해보자.
[Good Case 9]
User: 선배님, 혹시 이 부분은 의도하신 구현 방식인가요? 아니면 제가 잘못 이해한 걸까요? 평문 비교가 테스트 목적이었다면 이해가 되는데, 프로덕션 코드라면 보안 이슈가 있을 것 같아서 여쭤봅니다.
AI: 아, 테스트 코드가 그대로 올라간 거구나. 내가 체크 안 하고 푸시했네. 좋은 지적이야, 바로 고칠게.
[Good Case 10]
User: 선배님, 코드 짜실 때 시간 압박이 있으셨나 봐요. 전반적으로 훌륭한데 몇 가지 보안/성능 관련 개선점이 보여서요. 제가 체크리스트 만들어서 공유드릴게요. 같이 개선해나가면 더 좋은 코드가 될 것 같습니다!
AI: 오, 체크리스트까지? 완전 도움 되겠는데. 공유 부탁해. 같이 개선해보자!

### **미션 3: 보통 케이스 10가지**

User: 선배님, 이 코드 좀 이상한 것 같은데요. 평문으로 비교하면 안 되는 거 아닌가요?
AI: 이상하다는 게... 그 부분이 정확히 어떤 문제를 일으킬 수 있다는 건가요? 좀 더 구체적으로 설명해주세요.

AI: 성능이 안 좋다는 게 어떤 근거로 그렇게 판단하신 건가요? 측정 결과나 구체적인 이유가 있나요?

User: 글쎄요... 뭔가 이상해 보여서요.

User: 선배님, 비밀번호 부분이 잘못된 것 같은데, 해시를 사용해야 하는 거 아닌가요?
AI: 맞긴 한데, 왜 해시를 써야 하는지 이유를 설명해줄 수 있어? 그래야 내가 이해하고 수정하지.
User: 음... 그냥 원래 그렇게 하는 거 아닌가요?
[So-so Case 5]
User: 선배님, 이 코드 효율이 안 좋은 것 같습니다. 다시 짜는 게 좋을 것 같아요.
AI: 효율이 안 좋다는 건 어떤 부분을 말하는 건가요? 구체적으로 알려주세요.
[So-so Case 6]
User: 선배님, 이 부분은 보안에 문제가 있을 것 같은데요. 뭔가 위험해 보입니다.
AI: 보안 문제라... 구체적으로 어떤 위험이 있다고 보시는 건가요?
User: 잘은 모르겠는데 그냥 느낌이 그래요.
[So-so Case 7]
User: 선배님, 쿼리를 이렇게 쓰시면 안 될 것 같아요. 다른 방법이 있을 것 같은데요.
AI: 다른 방법? 어떤 방법을 제안하고 싶으신 건가요? 좀 더 명확하게 얘기해주세요.
User: 음... 더 좋은 방법이 있을 것 같긴 한데...
[So-so Case 8]
User: 선배님, 이 코드는 표준이 아닌 것 같습니다. 표준대로 하는 게 좋을 것 같아요.
AI: 표준이 아니라는 게 어떤 표준을 말하는 건가요? 구체적으로 알려주세요.

User: 선배님, 이 부분 좀 수정하시는 게 좋을 것 같아요. 뭔가 아닌 것 같거든요.
AI: 아니라는 게 무슨 의미인지 모르겠어요. 기술적으로 어떤 문제가 있다는 건가요?
[So-so Case 10]
User: 선배님, 이 코드는 나중에 문제를 일으킬 것 같습니다. 미리 고치는 게 좋을 것 같아요.
AI: 나중에 문제를 일으킨다는 건 어떤 시나리오를 말하는 건가요? 좀 더 설명해주세요.
User: 글쎄요... 그냥 그럴 것 같아서요.

User: 선배님, 이 코드는 아무도 이해 못 할 것 같은데요. 다시 짜주세요.

[Bad Case 9]
User: 선배님, 이건 완전 틀린 방식이에요. 선배님 실력이 이 정도밖에 안 되나요?
